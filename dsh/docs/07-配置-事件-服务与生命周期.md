# 07 · 配置、事件、服务与生命周期

这一课把插件开发的关键机制讲透：配置 schema、服务（Service）、事件模式、生命周期，以及工具执行流水线的挂钩点。

## 一、配置（Config）

### 基本写法

```ts
import Schema from '@deepseek-ai/schemastery'

export interface Config {
  apiKey: string
  timeout: number
  mode: 'fast' | 'accurate'
  verbose?: boolean
}

export const Config = Schema.object({
  apiKey: Schema.string().required(),
  timeout: Schema.number().default(30000),
  mode: Schema.union(['fast', 'accurate']).default('fast'),
  verbose: Schema.boolean().default(false),
})

export function apply(ctx: Context, config: Config) {
  // config 已校验且类型安全
}
```

- 用 `Schema.object(...)` 定义；**不要**导出普通对象（不满足 Standard Schema 接口）。
- schema 在**插件加载时**执行校验；非法配置让插件加载失败并给出明确错误。
- `cordis.yml` 里通过 `config:` 传值，未提供字段用 schema 默认值。

### 设计原则：无硬编码可调参数

```ts
// 错误：硬编码超时
const TIMEOUT = 30000

// 正确：可配置
export interface Config {
  timeoutMs: number   // 默认 30000
}
```

检验标准：**能否在 `cordis.yml` 中改变这个值，而不需要修改代码？** 不能的，就应该变成配置字段。

### 配置错误要响亮

在 schema 中表达自身完备的约束，让无效配置在**加载时**失败。对服务或已注册资源的引用需要依赖注入（下一节）。

## 二、服务（Service）

服务是插件向其他插件公开的**命名能力**。`tools`、`llm`、`agents`、`sessions`、`skills`、`commands` 都是服务。

### 使用服务

```ts
export const inject = ['tools']

export function apply(ctx: Context) {
  // ctx.tools 已就绪
  ctx.tools.register(/* ... */)
}
```

框架保证：`apply` 执行时 `inject` 声明的服务全部就绪；否则插件等待。

### 提供服务（类形态）

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

export default class MetricsService extends Service {
  static inject = ['llm']          // 服务也可以依赖服务

  constructor(ctx: Context) {
    super(ctx, 'metrics')          // 服务名 -> ctx.metrics
    // 在构造函数里做同步初始化
  }

  record(event: string, value: number) {
    // ...
  }
}
```

### 类型声明（声明合并）

让消费方拿到 `ctx.metrics` 的正确类型：

```ts
import { Service, type Context } from '@deepseek-ai/cordis'

declare module '@deepseek-ai/cordis' {
  interface Context {
    metrics: MetricsService
  }
}

export default class MetricsService extends Service {
  constructor(ctx: Context) {
    super(ctx, 'metrics')
  }
  record(event: string, value: number) { /* ... */ }
}
```

消费方：

```ts
export const inject = ['metrics']

export function apply(ctx: Context) {
  ctx.metrics.record('tool_call', 1)
}
```

### 依赖行为

- **必需依赖**：`export const inject = ['tools']`。服务消失时（如提供方被替换）插件自动卸载，服务恢复后自动重载。
- **可选依赖**：不写 `inject`，`ctx.get('metrics')?.record(...)`。

### 服务隔离

同一个服务可以有多个实例，不同插件组看到不同实例：

```yaml
- id: group-a
  name: '@deepseek-ai/cordis-plugin-group'
  group: true
  isolate:
    shell: true
  config:
    - name: '@deepseek-ai/dsh-bash-local'
      config: { timeoutMs: 5000 }
    - name: './src/plugin-a.ts'

- id: group-b
  name: '@deepseek-ai/cordis-plugin-group'
  group: true
  isolate:
    shell: true
  config:
    - name: '@deepseek-ai/dsh-bash-local'
      config: { timeoutMs: 60000 }
    - name: './src/plugin-b.ts'
```

`plugin-a` 和 `plugin-b` 各看到自己组内的 Bash 实例，互不影响。

## 三、事件模式详解

| 模式 | 触发方法 | await? | 短路规则 |
| --- | --- | --- | --- |
| `emit` | `ctx.emit(name, ...)` | 否 | 无返回值 |
| `bail` | `ctx.bail(name, ...)` | 否 | 首个非 `null`/`false`/`undefined` 终止 |
| `serial` | `await ctx.serial(name, ...)` | 是 | 首个非空值终止 |
| `parallel` | `await ctx.parallel(name, ...)` | 是 | 无返回值 |
| `waterfall` | `await ctx.waterfall(name, ...)` | 是 | 不调 `next()` 即短路 |

### `bail` 示例

```ts
const result = ctx.bail('some-check', input)

ctx.on('some-check', (input) => {
  if (shouldBlock(input)) return 'blocked'
  // 返回 null/false/undefined 继续下一个
})
```

### `waterfall` 示例（环绕中间件）

```ts
const output = await ctx.waterfall('my-plugin/transform', input, async () => input)

ctx.on('my-plugin/transform', async (_input, next) => {
  const downstream = await next()   // 调用下游
  return downstream.trim()          // 包装返回值
})
```

**单决策事件里短路是设计意图**：拥有决策权的策略监听器可以不调 `next()` 直接返回；只做标注/观察的监听器必须委托。

## 四、生命周期与清理

```
PENDING → LOADING → ACTIVE
                 ↘ FAILED
ACTIVE → UNLOADING → DISPOSED
```

- `apply` 抛异常 → FAILED。
- 必需服务消失 → ACTIVE → DISPOSED；服务恢复 → 重新加载。
- `fiber.dispose()` 保证：移除该插件的全部注册 → 递归卸载子插件 → 等所有异步清理完成后 resolve。
- 处置器按注册顺序**逆序开始**，异步处置器**并发**执行。有顺序依赖的清理放进同一个 `ctx.effect()` 的 disposer 里串行等待。

## 五、工具执行流水线：挂钩点

工具的执行贯穿一条流水线，每个阶段都有对应事件。**尽量别把部署策略内建到工具里**，用这些扩展点：

| 扩展点 | 用途 | 特性 |
| --- | --- | --- |
| `tools/pre-execute` | 可扩展的**允许/拒绝/询问**策略 | waterfall；`{ kind: 'allow' \| 'deny' \| 'ask', reason? }` |
| `ctx.tools.guard()` | **单调的最终拒绝**，后续监听器无法撤销 | 返回拒绝原因即终止 |
| `tools/execute` | 包裹分发：超时/重试/指标 | `exec.signal` 可替换 |
| `tools/post-execute` | 替换展示内容或返回值、阻止结果、附加模型可见上下文 | 注意：替换内容不阻止程序化访问 `value`；保密策略会屏蔽/替换值 |
| `tools/result` | 观测**不可变的归一化结果**而不改变它 | 审计/捕获 |

### 权限门禁示例（hook 插件）

```ts
import type { Context } from '@deepseek-ai/cordis'
import type { PreToolDecision, ToolExecution } from '@deepseek-ai/dsh-tools'

export const name = 'permission-gate'

export function apply(ctx: Context) {
  ctx.on('tools/pre-execute', async (exec: Readonly<ToolExecution>, next): Promise<PreToolDecision> => {
    if (!(await isAllowed(exec))) {
      return { kind: 'deny', reason: 'Denied by policy.' }
    }
    return next()
  })
}
```

这是 waterfall 形态的**可重排策略层**。需要不变式级别的单调最终拒绝时用 `ctx.tools.guard()`；需要包裹分发生命周期时用 `tools/execute`；显式结果变换用 `tools/post-execute`；对不可变最终结果的受限观察用 `tools/result`。

### 工具结果的观测

`tools/result` 观察不可变结果，例如：

```ts
export function apply(ctx: Context) {
  ctx.on('tools/result', (exec, result) => {
    audit.log({ name: exec.name, ok: !result.isError })
  })
}
```

## 六、功能 → 机制映射（节选）

所有产品功能都能映射到某个文档化扩展点上的监听器——没有一行修改主循环：

| 功能 | 机制 |
| --- | --- |
| 内置工具 | `ctx.tools.register()`，schema 自动流入系统提示词组装 |
| 权限系统 / AskUserQuestion | `tools/pre-execute` 返回 `ask` + `ctx.approval` 应答 |
| 上下文压缩（自动 + 手动） | `ctx.compaction` seam + 在 `agent/pre-step` 做压力检查 |
| 系统提示词可配置 | `ctx.systemPrompt.section()`，支持排序与作用域局部覆盖 |
| 子 agent 委派 | `ctx.subagents` 提供方注册表 + `dsh-tool-subagent` |
| MCP | 每个服务器一个插件：发现工具 → `ctx.tools.register()` |
| skill | section + 工具注册；调用时 `inject()` 注入 skill 内容 |
| 定时任务 | 插件注册面向模型的调度工具；到期用 `followup(...)` 投递 |
| UI | 监听 `agent/assistant-stream`（实时 chunk）与 `session/event`（持久 settlement）；输入 → `followup()` |
| 模型适配器 | 通过 `registerAdapter` 注册 `LlmAdapter` 子类 |
| 插件热重载 | 每个注册都是 `ctx.effect`，HMR 直接生效 |
