# 10 · 开发贡献与进阶

这一课面向想给 harness 本身写插件、或参与 dsh 开发的读者。

## 1. 搭建源码开发环境

前置条件：

- Node.js `^22.19.0 || >=24.0.0`（CI 覆盖 22.19、24、26）
- 启用 Corepack 的 pnpm（仓库固定 `pnpm@11.7.0`）
- Git ≥ 2.26
- 可选：DeepSeek API Key（用于真实 API 的 e2e 与演示）

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
corepack enable
pnpm install
pnpm run typecheck      # 成功退出即表示搭建完成
```

`pnpm install` 会通过 `scripts/install-lefthook.mjs` 配置 worktree 本地的 Lefthook Git 钩子。若因缓存或跳过 `postinstall` 而缺钩子：

```sh
node scripts/install-lefthook.mjs
```

> Windows 与 WSL 2：把检出目录、依赖、工具链放在**同一操作系统环境**里；跨文件系统访问会给 Git / 安装 / 构建带来大量 I/O 开销。

## 2. 构建与运行

```sh
pnpm run build          # 完整构建（Host + Client + Web），必需的产物准备
pnpm run start:web      # 用源码启动器 serve 已构建产物（等于 pnpm dsh web）
pnpm run dev:web        # 构建 + serve + 源码改动时重建 client bundle
pnpm run start:desktop
pnpm run dev:desktop
```

- 根构建顺序：Host tsc → Host tsdown（含 Typert）→ Desktop bundle → Client tsc → Client tsdown → Web 构建。
- `pnpm run build` 会内联版本、七位 commit 与 dirty 标记；`build:official` 是等价于 CI/release 的跨平台本地命令。
- `dev:web` 支持 `--skip-build` 复用现有产物、`--no-serve` 只跑重建 watcher。
- 启动器**不检查产物是否最新**：陈旧 bundle 可能继续跑旧代码。

源码 headless 演示：

```sh
pnpm dsh --profile headless "summarize this workspace"
pnpm run demo:ptc -- "summarize this workspace"   # PTC 代码式工具演示
```

环境变量放在仓库根目录被 gitignore 的 `.env`：

```sh
DEEPSEEK_API_KEY=sk-...
DEEPSEEK_BASE_URL=https://...   # 可选
```

## 3. 检查与门禁

```sh
pnpm run typecheck      # 完整 Host lib 阶段 + Client tsc
pnpm run test           # 构建 native system 后跑 vitest
pnpm run lint           # oxlint
pnpm run check:all      # 全面本地门禁集（独立于 Git 钩子）
pnpm run hygiene        # publint + NodeNext 类型消费校验
pnpm run doc-sync       # 文档同步（含生成目录、类型粘贴校验）
```

- 新 worktree 在 `pnpm run build` 之前没有打包的 JS 与声明文件；用到产物 `lib/` 的检查要先构建。
- Git 钩子：`pre-commit` 做配对文档与暂存 lint、`pre-push` 跑 `typecheck`；钩子**有意不跑测试/快照/构建/hygiene**。
- 贡献者只需运行**与改动行为相关**的检查；CI 负责全量覆盖率、产物冒烟与 Node 兼容矩阵。

## 4. 仓库结构要点

- **Host 与 Client 两个 aggregate**：Host 包进 `tsconfig.host.json`，Client 包进 `tsconfig.client.json`；少数拆分包含两套 leaf 配置。
- 新包只登记进**一个** aggregate（除非是共享 leaf）。
- 静态分析与测试通过 `tsconfig.base.json` 的 `paths` 把 workspace import 解析到 `src`。
- `vendor/` 是以 vendor 方式引入的 cordis；改 vendor 代码前先读 `vendor/README.md` 并同步更新 manifest。

```
apps/cli       # 启动器、profile、CLI 参考
apps/web       # 浏览器应用
apps/desktop   # Electron 桌面
packages/core  # session / tools / agent / agent-loop / scope / system-prompt
packages/llm   # llm / llm-deepseek / llm-pi-ai
packages/host  # plugin-inventory / webserver
packages/client# ui-* 浏览器插件
packages/boot  # app-boot / plugin-manager / cmdline / hmr
packages/*     # skill / mcp / sandbox / subagent / plan / todo / schedule …
docs/          # 官方文档
scripts/       # 构建、门禁、生成
```

## 7. 贡献流程与约定

- 面向 agent 的仓库规则见根目录 `AGENTS.md`（`CLAUDE.md` 是它的软链）。
- 贡献流程见 `CONTRIBUTING.zh.md`；每个 PR 只做一件事，选覆盖改动表面的最小检查集。
- **TODO 标签**（按紧急度）：
  - `FIXME`：应阻塞新版本发布的问题
  - `TODO`：应尽快修复
  - `XXX`：也许某天会修，最低优先级
- 文档为**中英配对**：`.i18n.yaml` 记录使用 Git 默认文本合并；改了一侧要同步另一侧，然后 `pnpm run verify-translation-pairing --write <pair>`。
- 子系统页里粘贴的类型用 ` ```ts type-equiv ` 围栏，并在 `scripts/type-equiv.manifest.json` 登记源文件与符号；改类型不更新粘贴内容会让门禁失败。
- CI 门禁清单以 `scripts/run-gates.ts` 与 `.github/workflows/ci.yml` 为准。

## 8. 进阶方向

| 想做 | 切入点 |
| --- | --- |
| 让模型多一个工具 | `ctx.tools.register(defineTool({...}))` |
| 拦截/审批工具调用 | `tools/pre-execute` waterfall；不变式用 `ctx.tools.guard()` |
| 改系统提示词 | `ctx.systemPrompt.section()`（排序 + 作用域局部覆盖） |
| 注入上下文 / 主动唤醒 | 工具里 `exec.agent.inject(...)`；定时器用 `followup(...)` |
| 接一个模型后端 | 实现 `LlmAdapter` 子类并 `registerAdapter` |
| 接 MCP 服务器 | 每个服务器一个插件：发现工具 → `ctx.tools.register()` |
| 做 Web UI 面板 | 注册 `ConversationNodeDefinition` 与 chat renderer；监听 `agent/assistant-stream` |
| 子 agent 委派 | `ctx.subagents` 提供方 + 已交付的 `dsh-subagent-*` 组合包 |
| 长期任务编排 | `ctx.workflowEngine` + `workflow` 工具 + PTC 工作流引擎 |
| 沙箱后端 | `ctx.sandbox` 后端（landlock / sandbox-exec / bwrap） |
| 自定义协议客户端 | 把协议对端接入 `ctx.agents`，参考 `packages/acp/acp` |
