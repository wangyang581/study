# 02 · 安装与运行

## 1. 前置条件

| 场景 | 要求 |
| --- | --- |
| 只运行（npm） | Node.js（建议 22.19+ 或 24+） |
| 从源码运行 / 开发 | Node.js `^22.19.0 \|\| >=24.0.0`，启用了 Corepack 的 pnpm（仓库固定 `pnpm@11.7.0`） |
| Git 相关功能 | Git ≥ 2.26 |
| 真实模型调用 | 一个 DeepSeek API Key（见第 03 课） |

启用 pnpm：

```sh
corepack enable
pnpm --version   # 应能解析到 11.7.0
```

## 2. 方式 A：通过 npm 运行（先体验）

```sh
npx @deepseek-ai/dsh web
```

- 默认在 `http://127.0.0.1:3080` 启动 Web UI，并在**本机**用默认浏览器打开。
- 通过 SSH 启动时只打印宿主机 URL（本地转发地址由 SSH 客户端/编辑器持有），不会尝试打开浏览器。
- `--no-open`：只启动服务器，不打开浏览器。

```sh
npx @deepseek-ai/dsh web --no-open
npx @deepseek-ai/dsh web --port 3081
```

Web 参数的完整含义见第 04 课与官方 [`apps/cli/README.zh.md`](https://github.com/deepseek-ai/deepseek-harness/blob/main/apps/cli/README.zh.md)。

> `dsh` 进程会把**启动时所在的目录**作为默认文件系统位置；全新的 Web UI 不会自动选中工作区，需要你手动添加。

## 3. 方式 B：从源码运行（要开发插件时）

```sh
git clone https://github.com/deepseek-ai/deepseek-harness.git
cd deepseek-harness
pnpm install
pnpm run build        # 准备仓库产物（必须，否则启动缺产物）
pnpm dsh web
```

- `pnpm run build` 准备产物；`pnpm dsh web` 直接使用已构建产物，不会重新构建。
- 源码模式通过 `node --import tsx/esm apps/cli/src/bin.ts` 启动，所以插件 `.ts` 源码无需编译即可加载。
- 启动器**不会检查产物是否最新**：旧的 client bundle 可能继续跑旧代码，改了前端要重新构建。

常用开发命令（Web 与 Desktop 共用一对）：

```sh
pnpm run start:web       # 用源码启动器 serve 上一次 build 的产物
pnpm run dev:web         # 先 build，再 serve，并在源码改动时重建 client bundle
pnpm run start:desktop
pnpm run dev:desktop
make web / make dev-web  # 等价的 Make target，ARGS='--no-open' 转发参数
```

## 4. Profile：选择运行哪种应用

`dsh` 通过**具名 profile** 选择应用形态，随发行版交付的模板有：

| Profile | 形态 | 说明 |
| --- | --- | --- |
| `web` | Web UI | 默认；浏览器应用 + HTTP 服务器 |
| `headless` | 一次性任务 | `dsh --profile headless "run the tests"`，不挂服务器、不开端口 |
| `sdk` | TypeScript SDK | stdio 承载 JSON-RPC |
| `sdk-minimal` | 最小 SDK | 独立组合树，固定 `danger-full-access`，无 fs 工具/指令发现/SQLite |
| `acp` | ACP | stdio 承载 Agent Client Protocol，仅供自动化 |

选择方式：`dsh --profile <name>`，或用简写 `dsh web` / `dsh headless`。注意 `plugin` 是管理命令，同名 profile 要用 `--profile plugin` 选择。

```sh
# 一次性任务，stdout 只打印最终文本，reasoning 增量流式写入 stderr
pnpm dsh --profile headless "summarize this workspace"
```

## 5. CLI 参数速查

| 参数 | 作用 |
| --- | --- |
| `--profile <name>` / `dsh <name>` | 选择 profile |
| `--patch <file>` | 叠加一层 patch overlay（可重复） |
| `--dump-default-config` | 只打印组合包各层 |
| `--dump-config` | 打印含 profile/home/argv 层的完整组合配置树 |
| `--dump-config-schema` | 输出组合配置的 JSON Schema（与上两者互斥） |
| `--from-default-profile <t>` | 用随附模板创建 profile |
| `web` 参数 | `--host`、`--port`、`--public-url`、可重复的 `--trusted-host`、`--no-open` |

`--dump-*` 会初始化缺失的 profile 文件，并在注释中标明每一行由哪个文件提供、哪些 overlay 改过它。**它不会运行应用参数提供方**，所以展示的是解析应用参数之前的树；若调用里带了应用参数，dump 会拒绝。

```sh
dsh --profile web --dump-config
```

## 6. Harness home 与目录布局

默认在 `~/.dsh`，可用 `DSH_HOME` 覆盖：

```
~/.dsh/
├── profiles/
│   └── web/
│       ├── package.json          # profile 依赖 + dsh.profile.bundles
│       ├── cordis.patch.yml      # 你的 patch 层
│       ├── compatibility.json    # 版本豁免（可选）
│       └── pnpm-workspace.yaml
├── logs/                         # 启动诊断日志 startup-<ts>-<uuid>.log
├── .credentials.yaml             # 模型 provider 凭据
├── .env                          # 机器级环境（与 API key 放一起）
└── cordis.patch.yml              # home 级共享 patch 层
```

## 7. 启动诊断与排错

- **构建产物缺失**：先从源码启动会因模块解析错误失败，先跑 `pnpm run build`。
- **必需插件激活失败**：CLI 先打印失败插件与原始堆栈，再列出等待中的插件和缺失服务；末尾 `Full diagnostics:` 指向 `$DSH_HOME/logs/startup-<timestamp>-<uuid>.log`，退出码 1。
- **端口/主机**：CLI 有意不支持 `--host 0.0.0.0`，会以用法错误退出；需要对外发布请用反向代理并配 `--public-url` + `--trusted-host`。
- **关闭**：进程关闭时插件树最多 5 秒完成 dispose；首次 `SIGINT`/`SIGTERM` 优雅排空，第二次立即强退。
